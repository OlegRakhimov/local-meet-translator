# Local Meet Translator 1.0.29 — реализация исправлений

## 1. Импорт PDF и DOCX

### Маршрут данных

```text
Пользователь выбирает файл
→ Electron dialog
→ candidate-profile-store.importFromPath()
→ document-text-extractor
→ нормализованный текст
→ поле resumeText
→ ручная проверка и сохранение профиля
```

`candidate-profile-store` принимает `.json`, `.txt`, `.md`, `.pdf` и `.docx`. JSON остаётся импортом структуры профиля. Остальные форматы попадают только в `resumeText`; массив `confirmedFacts` не создаётся из текста автоматически.

### DOCX

DOCX является ZIP-контейнером. Реализация не запускает Word и не извлекает файлы на диск. Она:

1. читает центральный каталог ZIP;
2. допускает только стандартное хранение и deflate;
3. ограничивает размер исходного документа, одной записи и общий распакованный объём;
4. читает `word/document.xml`, header/footer, footnotes/endnotes;
5. преобразует абзацы, таблицы, переносы и XML entities в обычный текст.

Это уменьшает поверхность атаки и защищает от ZIP bomb в рамках заданных лимитов.

### PDF

PDF извлекается через локальный Poppler `pdftotext`:

```text
pdftotext -layout -enc UTF-8 -nopgbrk <input.pdf> -
```

Процесс запускается с `shell: false`, не принимает составную командную строку, имеет таймаут и лимит stdout. Содержимое документа не отправляется через bridge или OpenAI. Если PDF содержит только изображения, возвращается ошибка о необходимости OCR.

Во время Windows build скрипт находит настоящий `pdftotext.exe`, копирует его и соседние DLL в `document-tools/poppler`, проверяет запуск, а после electron-builder повторно проверяет наличие и SHA-256 упакованного файла.

## 2. Режим соблюдения правил экзамена

Реализован безопасный режим вместо маскировки от прокторинга. Значение хранится как:

```text
EXAM_COMPLIANCE_MODE=true|false
```

При включении `config-store` принудительно сохраняет в `false` настройки помощника, автоанализа, телесуфлёра и content protection. `assistant-overlay` и `subtitle-overlay` повторяют это ограничение при нормализации настроек.

Main process дополнительно блокирует:

- генерацию ответа на вопрос;
- анализ coding follow-up;
- изменение существующего решения;
- AI-классификацию реплик активной coding-задачи;
- генерацию learning aids;
- команды открытия/управления помощником, кроме безопасных `hide`, `clear`, `rehome`.

Такое дублирование намеренно: отключение кнопки в renderer само по себе не является границей безопасности. Даже прямой IPC-вызов получает структурированный ответ `blocked=true`. При первом включении сохраняется небольшой JSON-снимок только управляемых булевых настроек; при выключении режима предыдущие значения восстанавливаются, после чего снимок удаляется.

Режим отключает Electron content protection, потому что при соблюдении правил приложение не должно пытаться исключать свои окна из захвата. Он не скрывает процессы, расширение, виртуальные устройства или сетевые соединения.

## 3. Интеграция DESKTOP_BLUR_STATE

### Расширение

Исправленное Edge-расширение вычисляет видимость как:

```text
document.visibilityState === "visible" && document.hasFocus()
```

и передаёт изменение при `focus`, `blur`, `visibilitychange`, `pagehide`, а также периодически синхронизирует состояние.

### Desktop

`POST /extension-client/armed` теперь читает `data.visible` и передаёт его в `ExtensionClientRegistry` без замены на `true`.

Реестр:

- назначает active только visible + armed client;
- очищает active при переходе клиента в hidden;
- запрещает `markActive()` для hidden client;
- сортирует кандидатов: visible → active → armedAt → lastVisibleAt → lastSeen.

Результат endpoint содержит фактические `visible` и `active`. Поэтому desktop не продолжает направлять `start/stop/release` вкладке, которая ушла в фон, если доступна видимая вкладка встречи.

`desktopCommandSeq` остаётся сохранённым ACK-курсором Edge-расширения. Видимость отвечает за выбор адресата, sequence — за одноразовое выполнение команды. Это независимые, но согласованные части протокола.

## 4. Воспроизводимая Windows-сборка

Локальный entry point не изменился:

```text
BUILD_DESKTOP_WINDOWS.cmd
```

Скрипт теперь проверяет и упаковывает:

- Java bridge JAR;
- минимальный Java runtime;
- standalone voice-conversion EXE;
- Chrome/Edge/Firefox extensions;
- Poppler `pdftotext.exe` и его DLL;
- Electron desktop.

После сборки проверяются ожидаемые файлы, минимальный размер установщика и совпадение SHA-256 runtime-компонентов. Создаются installer, `.sha256` и `RELEASE_MANIFEST.json`.

GitHub Actions workflow использует тот же entry point, а не отдельную упрощённую команду. Это исключает ситуацию, когда CI и локальная release-сборка создают разные комплекты файлов.

## 5. Ограничения

- OCR не реализован; image-only PDF не распознаётся.
- Anti-proctoring/stealth не реализован и не является целью режима соблюдения правил.
- Готовый Windows installer должен собираться на Windows runner или Windows-машине; исходный архив сам по себе не содержит Windows EXE.
